## Data Model and Lifecycle

- [ ] CHK001 Does FR-002 ("every notebook except a kitchen notebook MUST have exactly one owner") hold after FR-006 deletes a deleted user's memberships, given that the contract allows `owner_alias: null` "when no owner remains"? [Conflict, Spec §FR-002, §FR-006, contracts §The notebook object]

- [ ] CHK003 Does the spec say what happens to a notebook's kitchen links when its owner leaves or is removed from the kitchen before S-057 exists, and whether the kitchen's members can still read it in the meantime? [Gap, Spec §Assumptions, PRD §1.5 H]
- [ ] CHK004 Is "signup kitchen" defined in the spec in terms that can be checked, or only in research R4 ("the oldest kitchen the person owns")? [Clarity, Assumption, Spec §FR-020, §Assumptions]
- [ ] CHK005 Do FR-020 ("if they no longer belong to it, linked to no kitchen") and research R4 agree when the person deleted "My kitchen" and later created another kitchen, which the oldest-owned rule would then treat as the signup kitchen? [Conflict, Spec §FR-020, research.md §R4]
- [ ] CHK006 Is the person's catalog defined the same way in FR-010 ("the notebooks the owner already owns or is a member of"), FR-014, and research R7, which also counts the kitchen notebooks of their kitchens? [Consistency, Spec §FR-010, §FR-014, research.md §R7]
- [ ] CHK007 Does the spec state that a kitchen notebook's members are the kitchen's members, with access "member", or is that only in the contract and data model? [Gap, Spec §FR-012, §FR-013, contracts §GET /notebooks/{notebook_id}]
- [ ] CHK008 Is the rule "the default notebook is linked only when it is created, never later" stated as a requirement, not only as an edge case, so a rejoined or renamed signup kitchen has a defined outcome? [Clarity, Spec §Edge Cases, §FR-007]
- [ ] CHK009 Are limits on notebook names defined, given that "{alias}'s Notebook ({kitchen name})" joins two user-chosen texts of their own lengths? [Gap, Spec §FR-008]
- [ ] CHK010 Is the clarify Q3 rule (the default notebook is linked to the signup kitchen) reflected in PRD flow H and J1a, which the spec's Assumptions name as the source that wins on conflict? [Consistency, Spec §Assumptions, plan.md §Follow-ups]

## Capture Step and Concurrency

- [ ] CHK019 Does the last sentence of FR-008 ("the member picks among the kitchen's notebooks where their access is owner or member (FR-013)") exclude the kitchen notebook, which FR-013 lists with access "member" and FR-008 forbids as a capture target? [Conflict, Spec §FR-008, §FR-013]
- [ ] CHK020 Is the outcome defined when an archived kitchen already has a capture notebook for the member, given that FR-009 forbids only a new notebook and spec 016 FR-033 refuses every capture in an archived kitchen? [Conflict, Spec §FR-009, spec 016 §FR-033]
- [ ] CHK021 Is the scope of "simultaneous first requests" stated (one member in one kitchen), so two different members' first captures in one kitchen are expected to create two notebooks? [Clarity, Spec §FR-008, §SC-002]
- [ ] CHK022 Is the race between a first `GET /notebooks/default` and a first capture in the signup kitchen covered, since both can create the default notebook? [Coverage, Gap, Spec §FR-007, §FR-020]
- [ ] CHK023 Is the outcome defined when a person already has a default notebook that is not linked to their signup kitchen (created while they were not a member) and they capture there: a new "(My kitchen)" notebook, or the default? [Edge Case, Clarity, Spec §FR-020, §User Story 2 scenario 9]
- [ ] CHK024 Does the spec say that a notebook created by the capture step is undone when the recipe save that called it fails, so a failed save leaves nothing behind, like a discard? [Recovery, Gap, Spec §FR-008, §SC-008]
- [ ] CHK025 Is the capture step's behavior for a caller without an alias defined, given that the alias check (FR-016) covers routes and the step has no route? [Gap, Spec §FR-016, §FR-021]
- [ ] CHK026 Is a pick allowed when the member has exactly one candidate, and is a pick refused with the same answer when there are no candidates? The data model says yes to both; the spec doesn't say. [Clarity, Spec §FR-008, data-model.md §Domain]
- [ ] CHK027 Do the Acceptance Scenarios of User Story 2 cover the archived-kitchen case, which FR-009 requires? [Coverage, Spec §User Story 2, §FR-009]
